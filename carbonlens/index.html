The problem

Content review was the last thing still entirely manual

IBM Power HMC is a complex enterprise interface with hundreds of screens and strict Carbon Design System content guidelines. Unlike layout — which Figma makes inspectable — content quality had no tooling inside the design environment.

01

Title case throughout

Carbon requires sentence case. Designs regularly shipped "Flow CONTROL", "View Feedback", "Physical Port" — caught only during code review, if at all.

02

Placeholder copy at handoff

Error messages, empty states, and tooltips were left as "Error message goes here" because writing correct copy in the moment took time designers didn't have.

03

Verb-less button labels

Buttons reading "Click to take actions" or "Submit" violated Carbon's verb-first guideline — a consistent pattern that no automated check surfaced.

04

Manual spacing documentation

Translating pixel values into $spacing-XX tokens for every handoff required a manual cross-reference against the Carbon scale. Hours per screen.

"Review cycles took 2–3 days. Spacing documentation alone could take an afternoon per screen. Content issues still slipped through at handoff because nothing automated caught them while designers were working."

— Project context from the CarbonLens product brief (paraphrased, not a direct quote)
The solution

Three focused modes. One shared frame selection.

CarbonLens lives in the Figma plugin panel. A designer selects a frame, picks a mode, and clicks Scan. Each mode is narrow enough to be fast, deep enough to be useful.

🔍

Reviewer

Scans every text node against ten Carbon rules. Groups violations by rule. Each issue shows original text, a suggested fix, the Carbon guideline, and a Locate button.

Content linter
✍️

Writer

Reads the frame's content signals and sends them to an AI model. Returns structured spec cards across five categories: field errors, notifications, actions, and more.

AI copy generation
📐

Handoff Partner

Maps every auto-layout spacing value to the nearest Carbon $spacing-XX token, then draws zone-fill annotation overlays directly on the Figma canvas.

Canvas annotations

Two AI providers. One toggle.

Writer and Reviewer both route through a configurable AI provider. The choice was intentional — corporate design environments have strict data-residency requirements. Ollama runs completely offline: content never leaves the machine. watsonx.ai provides IBM Granite models for teams who need enterprise-grade output and IBM Cloud compliance.

Settings persist via figma.clientStorage. The manifest's networkAccess allowlist names every permitted domain — no accidental exfiltration is possible. Context fields (screen intent, focus constraints) are fed directly into the AI prompt before each scan.

Ollama · local · offline-first
watsonx.ai · IBM Granite · 5 regions

Reviewer — ten rules, zero server calls

The rule engine runs entirely client-side. Results appear without any network request. Rules are deterministic — they fire when the text matches the pattern. AI enhancement is layered on top only for violations requiring contextual judgment.

Rule What it catches
title-caseMulti-word capitalisation and long ALL-CAPS strings not matching a known acronym list (IBM, I/O, VLAN preserved)
missing-verbButton labels that do not open with one of ~30 recognised action verbs
vague-labelGeneric labels: "Submit", "Click here", "OK", "Proceed"
filler-wordsPhrases stripped on sight: "Please ", "In order to", "Simply", "Click here to"
spelling200+ UI-copy misspellings plus repeated-character detection
ellipsis-misuseEllipsis on buttons, labels, or headings — only valid in body text per Carbon
Reviewer results. 6 violations across 56 text nodes. Summary bar shows issues / clean / total. Each violation group is expandable with original text, suggested fix, and a canvas Locate button.

Writer — screen-aware AI copy

Writer builds a structured prompt from the frame's existing text. An optional "What is this screen?" field adds intent context — user role, access level, purpose. A "Focus / constraints" field narrows the scan to specific node types. The AI returns typed spec cards that can be edited and copied individually.

Writer results. 9 items generated for the VIOS properties screen: screen description, field errors with cause and resolution, helper text, and 2 notifications. Each card has Edit and Copy actions.

Handoff Partner — token annotations on canvas

For each auto-layout frame the plugin reads padding and gap values, maps each pixel to the nearest Carbon token (2px = $spacing-01 through 96px = $spacing-12), then draws two artefacts: a zone-fill overlay at exact frame coordinates, and a spec panel 48px to the right. Both persist without the plugin open — developers see them in Figma.

Handoff Partner. Zone-fill annotations drawn over the "Create Ethernet logical port" modal. Spec panel lists typography and spacing tokens. Plugin confirms 54 nodes · 4 sections annotated.
Process

How it was built

CarbonLens was built with IBM BOB as the primary development partner. Carbon MCP and Figma MCP provided design-system authority and canvas context during the build — not at runtime. The plugin itself runs entirely inside Figma's sandboxed environment.

architecture — dev time vs. runtime

Development time
IBM BOB → Carbon MCP → Figma MCP → code.ts + ui.html → npm run build → dist/
Plugin runtime
Figma canvas → manifest.json → dist/code.js + dist/ui.html → Ollama or watsonx.ai

IBM BOB, Carbon MCP, and Figma MCP are development-time tools only. At runtime the plugin communicates directly with the Figma API and with Ollama (localhost:11434) or watsonx.ai — no proxy, no middleware in the critical path.

dev partner

IBM BOB

Primary development partner for the full build. Generated the initial architecture, iterated on the Carbon rule engine, wrote the Handoff Partner canvas-drawing code, and debugged TypeScript errors. Brief to working v1.0 in ~3 days.

design system

Carbon MCP

Provided authoritative Carbon Design System documentation — the correct $spacing-XX token scale, type tokens, and content writing rules (sentence case, verb-first buttons, error-message structure).

canvas context

Figma MCP

Allowed inspection of actual IBM Power HMC design files during development — layer names, component hierarchies, text-node structures — which informed the inferComponentType() logic.

plugin config

Figma Manifest

Defined via manifest.json with main: dist/code.js and ui: dist/ui.html. Network allowlist explicitly names IBM IAM, watsonx.ai, and localhost:11434. Only currentuser scope requested.

runtime AI

Ollama + watsonx.ai

Two providers, one toggle. Ollama runs locally — llama3.2 recommended, qwen2.5:1.5b for 2-second responses. watsonx.ai provides IBM Granite 3.3 8B or Llama 3.3 70B with 5 region options.

build

TypeScript + Webpack

Two entry points: code.ts (Figma sandbox thread) and ui.html (iframe, inline JS). Webpack bundles to dist/. npm run build for production, npm run watch for development.

Design decisions

Thinking behind the product

Five decisions shaped how CarbonLens works — each driven by a real constraint: speed, security, developer reuse, or the limits of Figma's sandbox.

01

Rules run first, AI second

The Reviewer checks content instantly using a built-in rule set — no internet needed. AI only kicks in for the trickier issues that rules can't catch reliably.

Trade-off: Some button names get flagged incorrectly. It's a known edge case.
02

Screen context is optional but powerful

Designers can describe what the screen does and who uses it. The AI uses that to write more relevant copy — skip it and you still get a useful result.

Challenge: Making it feel optional without hiding its value. Example placeholder text does the job.
03

Works offline or in the cloud

Some teams can't send data outside their network. Ollama runs the AI entirely on your machine. watsonx.ai is there when you need the cloud. One setting, no code changes.

04

Annotations live in the file

Spacing notes are drawn directly onto the Figma canvas — not just shown in the plugin. Developers see them without needing to open CarbonLens at all.

05

Scan many frames at once

Select multiple screens and run one scan. Issues that appear across many screens are grouped together — making it easy to spot copy problems that are systemic, not one-off.

Learnings

What I take from this

I had never built a plugin before

I had zero experience with Figma plugin development when I started. No TypeScript background, no idea how the Figma sandbox worked. I just knew the problem was real and worth solving. That was enough to start.

The tools made it possible

Learning how Figma MCP and Carbon MCP worked changed everything. Suddenly I could ask questions about the design system and get answers grounded in the actual spec — not guesses. IBM BOB helped me write and debug code I had never written before.

The problem was mine first

I built this because I was frustrated with my own workflow. Once I shipped it, the rest of the design team started using it too. That was the moment I realised the problem wasn't just mine — it was everyone's.

Now talking to the Carbon team

The work has caught the attention of the Carbon Design System team. We're now in early conversations about how parts of CarbonLens — particularly the rule engine — could be contributed back to Carbon for broader use.
