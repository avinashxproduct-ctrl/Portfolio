01

Project introduction

A single-page tool that holds a product's information architecture in one place and shows, at a glance, how far its screens have moved to the Carbon Design System.

  • GA Releases — one card per release, with a status breakdown and a detail panel.
  • IA Progress — the architecture itself: Theme → Epic → Feature, with status on every feature and a before/after progress view.

The hierarchy is the primary structure; all counts and percentages are derived from it — nothing is typed in separately.

02

Problem statement

A large enterprise product has many areas, many contributors and a migration to a design system that lands release by release. Three needs shaped the tracker. I have separated what I can evidence from the objectives I set.

Evidenced in the artifacts

  • The project's working rules name two reference sources for the same product: the architecture in design files, and release views on a project board. The tracker brings both into one page.
  • The first version of the tracker page carried a headline summary typed into the markup. When I audited it, that summary did not match the records underneath. The rebuilt version calculates every figure from the data.
  • Status and release information sat on each record, with no roll-up across themes or releases until the tracker provided one.

Design objectives

  • Give the architecture one home, with a clear hierarchy that can be scanned and expanded.
  • Make status and progress readable without opening every record.
  • Show release-level work next to the architecture, so migration progress can be followed across releases.
  • Keep summary figures derived from records, so they cannot drift from the detail.

05

How it was built

The tracker is a plain HTML, CSS and JavaScript page that reads one JSON file and renders everything from it. I directed the work as a designer and used an AI coding assistant for implementation. I have tried to say only what the project files show.

  1. Understand the architecture and the data

    Start from the product's existing structure and release plan, and settle the hierarchy — five themes, each with epics and features — and the status vocabulary used across both views.

  2. Decide that data drives the page

    The page renders from data.json. Counts, percentages and bars are calculated from records rather than typed in. This rule is written into the project's AI-assistant instructions.

  3. Build and iterate with an AI assistant

    I worked with IBM Bob to generate and revise the page and the data. Bob's edit history is recorded against commits in the project's git notes.

  4. Audit, fix and prepare a public version

    For this portfolio I audited the original, fixed its defects, replaced all data with a synthetic dataset, and tested the result in a browser.

06

Future scope

This is a plan, not something delivered. The tracker is evolving: it changes with the scope of the product, and the next step is to make it a dynamic, interactive tool.

  • Edit in the tool. Add and update real values directly in the tracker (statuses, releases, work items) instead of re-analysing the source boards and design files through an MCP each time.
  • Lower token usage. Reading everything through an MCP into an AI assistant uses a lot of tokens. Keeping the live values in the tool itself is intended to reduce that. I have not measured the saving.
  • Keep the data-driven rule. Totals and percentages would continue to be calculated from the records, so edits update every summary automatically.
  • Follow the product's scope. As themes, epics and features are added or reshaped, the hierarchy and views are meant to grow with them.
